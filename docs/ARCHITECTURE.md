# Architecture and maintainer notes

> **About this document.** It began as the private hand-over notes written during development and was edited for the first public release (v0). References to versions such as v729 to v731 and to dates are the project's pre-release numbering; they are kept because the explanations matter, not because you need the numbers. Where the notes talk about a "yard", they mean the business using the app. Known problems are listed in `../KNOWN_ISSUES.md`; some of the lessons below describe rules that the current code does not yet fully follow (for example the layout rules in lessons 45 to 57 and 65).


If you're picking this project up — human developer or another AI — read this first. It'll save you from re-discovering several things the hard way.

## What this is

**Yarding** is a complete ship-yard accounting tool: sales, purchases, expenses, payments, a real double-entry ledger, bank/cash account tracking, party (customer/vendor) statements, ship-level profit tracking, tax handling, and reporting. It was built for a ship-recycling yard, but is written generically — nothing in the app assumes any specific country, currency, or business beyond "a yard that buys and sells things and tracks money."

It ships as **one single HTML file** — no build step, no bundler, no server required to run it. Open it in a browser and it works. It can optionally connect to a Supabase project for multi-device sync; without that, it runs entirely offline against the browser's own IndexedDB.

## Where everything is

Everything — HTML, CSS, and JavaScript — lives in **`index.html`**. It's long (roughly 290KB). Don't go looking for separate files; there aren't any. Use your editor's search rather than trying to read it top to bottom.

Rough layout of the file, top to bottom:
1. `<style>` — all CSS, including CSS custom properties (`--sp-*` spacing scale, `--r-*` radii, colors) near the top.
2. Static HTML — the setup screen, login screen, app shell (sidebar, bottom nav, modal system), all present in the DOM from the start and shown/hidden via classes, not re-rendered from scratch.
3. `<script>` — one big inline script containing every module below.

Supporting files, for development and not for deployment:
- `tests/smoketest.js` -- the functional test suite (Node + jsdom). Run with `npm test`.
- `tools/check.js` -- syntax and sanity checks for the app file. Run with `npm run check`.
- `server/` -- the optional yard gate (a proxy) and its tests.

**Run `npm run test:all` and check the count before calling any change done.** jsdom does not do layout, so it cannot see clipped text, hidden buttons or touch problems; look at every screen you touch in a real browser at 320, 360 and 390 px wide. This app has a substantial test suite (500+ checks) because the codebase repeatedly had bugs that were invisible until tested properly -- see "Hard-won lessons" below.** This app has a real, substantial test suite (300+ checks) built up specifically because this codebase has repeatedly had bugs that were invisible until tested properly — see "Hard-won lessons" below.

## Core modules (inside the script)

- **`STATE`** — the single in-memory source of truth: `STATE.data` (all tables as arrays), `STATE.session` (who's logged in), `STATE.config` (company/mode/currency/templates), `STATE.view`.
- **`DB`** — the write path. `DB.insert/update/insertMany/upsertMany` write to `STATE.data`, then IndexedDB, then (if in cloud mode) Supabase — queueing to a local outbox on failure so nothing is lost offline.
- **`IDB`** — the IndexedDB wrapper. `IDB.open()`'s `onupgradeneeded` is strictly additive (`if(!db.objectStoreNames.contains(name))`) — it must never be changed to anything that could drop an existing store. This is what keeps replacing the HTML file safe for users' existing data.
- **`Ledger`** — the accounting engine. Every money movement goes through `Ledger.post(date, memo, lines)`, which rejects unbalanced entries. Higher-level helpers (`createInvoice`, `recordPayment`, `voidInvoice`, `voidPayment`, `createJournal`, advance handling) all ultimately call `post`. Nothing is ever hard-deleted — voiding posts a reversing entry and marks the record `voided`/`status:'void'`.
- **`Views`** — one function per screen, returning an HTML string rendered into `#view-root`. `Views.dashboard()`, `Views.invoiceList(kind)`, `Views.banking()`, `Views.settings()`, etc.
- **`Forms`** — modal form logic: rendering, dynamic rows (line items, tax rows, split-payment rows all share the same pattern), validation, and submission.
- **`Auth`** — login flow (role choice → code → identity → optional staff module-preference step), device reset, session state.
- **`UI`** — navigation (`UI.navigate`), the modal system (`UI.openModal`/`closeModal`), rendering orchestration.
- **`Backup`** — JSON/Excel export and import, module packages (scoped exports for handing off one category of work), all with preview-before-commit for imports.
- **`GenericSync`**, **`ModulePrefs`**, **`PrintMod`**, **`Charts`**, **`Icons`**, **`Branding`**, **`FolderBackup`** — smaller self-contained modules; names are self-explanatory.

## Data model

Tables (mirrored in IndexedDB locally and in Supabase in cloud mode): `accounts`, `parties`, `ships`, `items`, `bank_accounts`, `invoices`, `invoice_lines`, `transactions`, `transaction_lines`, `payments`, `advances`, `audit_log`, `settings`.

The SQL schema and every migration applied so far live inside `index.html` as the `SQL_SCRIPT` and `SQL_MIGRATION_ADVANCES` constants — search for those. Both are written to be idempotent (`create table if not exists`, `add column if not exists`) so they're always safe to re-run.

## Conventions worth knowing before you touch anything

- **Role model:** Admin and Staff, distinguished by two separate access codes (no per-user login system — identity is a name typed at login, stamped onto records via `whoAmI()`, not an auth mechanism). A yard can be set up "staff-only" (no admin code at all) — Settings, the Ledger view, and voiding are structurally unreachable in that case, by design.
- **Staff module preferences** (`ModulePrefs`) let a staff person restrict their own nav/dashboard to only the modules they use. Admin is never filtered.
- **Never hard-delete.** Everything voids instead, via a reversing ledger entry.
- **Tax** lives as `invoices.tax_breakdown` (an array of `{label, type, value, amount}`), with `invoices.tax` as the pre-computed total the ledger actually posts as one "Tax Payable" line.
- **Split payments**: `payments.split_group_id` links multiple payment records that together represent one real-world payment event (e.g. part cash, part bank). Invoice creation and standalone "record a payment" both go through the same `Ledger.recordPayment` call per split leg — don't special-case payment-at-creation again if you touch this.
- **Import is admin-only**, enforced inside the functions themselves, not just by page access. **Export is available to everyone.**

## Hard-won lessons (read before making UI/interaction changes)

These are real bugs that shipped and were later found and fixed. They're recorded here so they don't happen again.

1. **`svg{display:block}` with no override on `.icon`** caused any inline `icon + text` pattern to stack vertically unless it happened to be inside a flex container. One CSS rule caused several unrelated-looking "broken" spots. If you add a new icon usage, verify it sits inline.
2. **Hash-based navigation also fires a `popstate` event, not just `hashchange`** — and that `popstate` can arrive *after* something else has already happened, like a modal opening. The modal-close-on-back logic had no way to tell a stale event from a real back press, so it silently closed modals that had just legitimately opened. Fixed via a counter (`STATE._pendingHashPopstates`) that `UI.navigate` increments and the `popstate` listener decrements before treating anything as a genuine back press. If you ever touch navigation or the modal system, re-run the stress test in `smoketest.js` (search "rapid-fire navigation") before shipping.
3. **`window.print()` called in the same tick as writing the print content** can snapshot the page before it's actually painted, printing blank on some mobile browsers. Fixed by deferring `print()` two `requestAnimationFrame` ticks after setting the content. Any new print template goes through the same `PrintMod.show()` — don't call `window.print()` directly elsewhere.
4. **Testing by calling functions directly (`Views.x()`, `Forms.y()`) instead of actually clicking the rendered button** hides real bugs in the `onclick` wiring and in interaction timing — bug #2 above was invisible to function-call-style tests and only surfaced once tests started using real `element.click()`. When testing anything interactive, prefer finding and clicking the actual rendered element.
5. **`.row` had no default `gap`**, so a header + button combo that wrapped onto two lines on a narrow screen had zero space between them, looking broken. Fixed once at the CSS root rather than per-instance.
6. **Voiding an invoice must undo every side effect linked to it, not just its own ledger entry.** This has been missed twice: once for payments recorded against an invoice, once for an advance applied to one. Both times, the ledger reversal itself was correct, but a separate tracking table (`payments`, `advances`) was left showing the old, no-longer-true state. If you add any new kind of record that links to an invoice (`invoice_id` on anything), check whether `Ledger.voidInvoice` needs to know about it too.
7. **A one-time migration should check live data, not a "done" flag.** The invoice-numbering migration's first version set a flag the moment it found nothing to migrate — correct for a brand-new empty yard, but that flag then permanently blocked ever checking again, so an old-format backup imported later would never get migrated. Fixed by having the migration check "does anything actually still lack the new field" every time, which is self-healing regardless of when old data shows up, and cheap enough to just always do. Any future one-time migration in this codebase should follow that pattern, not a flag.
8. **An inline `style="grid-template-columns:..."` always beats a class's media query, no matter how the class is written.** A multi-field row (invoice lines, tax rows, split payments, journal lines) used exactly this to fit many fields in one row, which meant the row's column count could never actually respond to screen width — on a narrow phone it just shrank every column uniformly into unreadable slivers instead of wrapping. Fixed by moving every such row to a flex-wrap layout with a minimum width per field, which reflows naturally at any width with no breakpoint needed. If a future row needs several fields side by side, use that same flex-wrap pattern — never a fixed inline grid-template-columns.
9. **`fns[STATE.view]()` does not bind `this` to `Views`, even though `fns.reports` and `Views.reports` are the same function.** `this` binding follows the object a method is called *through*, not where it was defined — calling a copied-out reference via a plain dispatch table sets `this` to that table, not the original object. Every view that reads its own state via `this._something` (date ranges, filters, toggles) was silently reading nothing through that path, even though the code that *set* the state (e.g. `Views._from = ...`) was correct. This was real and had been live for a while: Reports' "Apply" date-range button almost certainly never actually changed what was displayed, and nothing caught it because nothing tested it. Fixed with `.call(Views)` at the one dispatch site in `renderView()` — if a future refactor changes how views are invoked, keep an explicit `this` binding, and add a test that actually re-reads state after setting it, not just that setting it didn't throw.
10. **`return new Promise(...)` is not the same as `return await new Promise(...)` inside a try/catch.** Every IndexedDB helper (`get`, `getAll`, `put`, `putAll`, `clearStore`) had this exact mistake: the surrounding try/catch looked like it would handle a failure, but without the inner `await`, a rejection from the returned promise (e.g. `getAll` on a table that doesn't exist) skips straight past that catch block instead of being caught by it. This caused a real, live bug — a blank, permanently stuck Dashboard with no error shown, reported directly by the user. Any time a function's whole body is `try { return new Promise(...) } catch {}`, check for this — it needs `await` before `new Promise` or the catch does nothing.
11. **A screen failing to render should never mean a blank page.** Before this, if any view function threw for any reason, `renderView()`'s `root.innerHTML = ...` assignment simply never happened, leaving whatever was there before (usually nothing) with zero indication anything went wrong. `renderView()` now wraps that call in a try/catch and shows a real error message with a way back to Dashboard. This is the single most valuable safety net in the app for diagnosing "it's just broken" reports — keep it intact through any future refactor of the render/dispatch path.
12. **A hang is not a throw, and no try/catch anywhere will catch one.** The blank-Dashboard bug took two passes to actually fix: the first pass (dead catch blocks in the IndexedDB helpers) was real and worth fixing, but wasn't the actual cause — the real cause was `IDB.open()` having no timeout and no `onblocked` handling, so a blocked connection (typically another tab still holding an older database version open) just hung forever with nothing ever throwing. No amount of try/catch anywhere else in the app can catch a promise that never settles. The lesson: any code that waits on a browser API with a "this could block waiting for something outside this tab's control" mode (IndexedDB version changes are the classic case) needs its own explicit timeout, not just error handling — silence and an infinite hang look identical to "still loading" from the outside, and are much harder to diagnose from a bug report alone.
13. **`Ledger.post()` is the one chokepoint worth over-validating.** Every money movement in the app routes through it, which makes it the cheapest possible place to stop bad data. Two real defects were found there: a `NaN` amount passed the balance check (`NaN - NaN` is `NaN`; `Math.round(NaN) !== 0` is `true`) and wrote `NaN` into the ledger, permanently poisoning every derived balance with no error at all; and negative amounts were accepted, which balance arithmetically while being meaningless in double-entry. Both are now rejected there. If you add a new kind of transaction, route it through `post()` rather than writing `transaction_lines` directly, and you inherit these guards for free.
14. **Balance-derived limits need enforcing in the engine, not just the form.** Advances could be applied or refunded well beyond what a party actually held — the form had a check, but the engine didn't, so any other path (or a form bug) drove the balance negative and produced a phantom balance everywhere it was displayed. The guards now live in `applyAdvance`/`refundAdvance` themselves. Assume forms are a convenience layer, not a safety layer.
15. **Anything read out of an imported file is untrusted, including its shape.** `(x || []).filter(...)` guards `null` and `undefined` but not a value that's simply the wrong type — a corrupted or hand-edited backup with a table set to a string crashed the import outright. Use the shared `asRows()` helper at every import boundary rather than `|| []`.
16. **Passing the existing test suite is not the same as being correct.** All five defects above were found by writing throwaway scripts that attacked the app from angles nothing had tested: empty yard, orphaned records, invalid amounts, corrupted imports, hostile text, extreme values, blank form submissions. The suite passed 451/451 before that hunt and every one of those bugs was live. When asked to verify the app is sound, write new adversarial probes — don't just re-run what already passes.
17. **Pick ONE mechanism for reversing a posted entry — voiding the transaction or posting a reversal, never both.** Every balance function here (`accountBalance`, `trialBalanceCheck`, `Reports.compute`, `bankTotal`) filters out transactions with `voided:true`. `voidInvoice` also posted an explicit reversing entry on top of that, so the amount was removed twice: voiding a 1,000 sale left income at -1,000 and the P&L reporting income that never existed. This shipped and went unnoticed because **the trial balance still reported "balanced"** — both sides moved together, so the app's own integrity check couldn't see it. Two lessons: (a) in this codebase the `voided` flag *is* the reversal, so never post a reversing entry as well; (b) "trial balance is balanced" proves debits equal credits, nothing more — it will not catch an amount being double-counted or double-removed. Assert on individual account balances, not just that the books balance.
18. **Never silently guess an ambiguous imported date.** Spreadsheet dates arrive as Excel serials, dd/mm/yyyy, mm/dd/yyyy, ISO, and free text. The importer converts what it can confidently read and explicitly flags what it can't, rather than falling back to a guess. A wrongly-guessed date isn't a visible failure — it lands the record in the wrong reporting period, where it is very hard to ever notice. Where genuinely ambiguous (both parts ≤ 12), it assumes day-first, matching regional convention, and this is documented at the code.
19. **Any template shipped with an example row must auto-skip that row on import.** People will forget to delete it. The example is marked with a fixed sentinel string and skipped, so the common mistake is harmless rather than creating a phantom record that then has to be found and deleted.

## Before changing or shipping anything

1. Run `npm run test:all`. The pass count must not go down and there must be no `FAIL` lines. (`npm run check` alone does the syntax and sanity checks; `npm test` alone runs the app suite.)
2. Check every screen you touched in a real browser at 320, 360 and 390 px wide, with a touch device or emulation, and with the keyboard open. There is no automated layout check yet (see `KNOWN_ISSUES.md`), and jsdom cannot see clipping.
3. If the change affects something clickable, write at least one test that finds and clicks the *actual rendered element*, not only one that calls the underlying function.
4. If you touched anything that writes several records, add a test that injects a failure part-way and asserts the data is identical afterwards.
5. Add an entry to `CHANGELOG.md`: what was reported, what was actually wrong, what changed, and what you did not verify.
6. Update the in-app Help and these docs if behaviour changed.

## More hard-won lessons

20. **Declare new top-level modules as `window.X = {...}`, never `const X = {...}`.** Everything in this app is wired up with inline `onclick="Module.method()"` handlers. A module declared with `const` at script top level is not a property of `window`, so those handlers can fail to resolve it — and the test harness, which reaches modules as `w.Module`, can't see it either. The Onboarding module was written this way and every one of its own buttons would have been dead in a real browser. Match the existing `window.Views = {...}` convention.
21. **Anything that opens a modal on a timer must check whether one is already open.** The post-login onboarding prompt fires ~400ms after boot; in that window a person can easily have tapped into a form, and replacing it would silently lose their input. `Onboarding.maybeShow()` bails out if `#modal-bg` is showing. Any future delayed or background prompt needs the same guard.
22. **When widening permissions, the tests asserting the old restrictions are not failures to be silenced — they're the checklist.** Opening staff access broke exactly the seven tests that asserted staff were blocked. Each one was rewritten to assert the new intended behaviour, which is what proves the change actually landed everywhere rather than just in the nav. Don't delete such tests; invert them.
23. **Nothing leaves the device unless the person connects a store.** The earlier "ask a question" AI feature was removed in v0 (it sent figures to an outside service). If a feature like it is ever added, it must be off by default, say plainly what is sent before anything is connected, send aggregates only, and never render a stored key back into the page.
24. **Expand repeating blocks BEFORE the general token pass in the template engine.** `renderCustomTemplate` does `{{#lines}}…{{/lines}}` first, then top-level `{{tokens}}`. Reversed, the general pass sees `{{description}}` inside the line block, finds no matching top-level token, and blanks it — so every row prints empty while the rest of the document looks fine. This exact bug shipped into testing.
25. **Changing the login flow must stay backward compatible or existing people are locked out.** Staff accounts (ID number + personal code) only activate once at least one account exists; a yard with none keeps using the shared staff code exactly as before. Any future auth change needs the same treatment — the upgrade path matters more than the new path, because the new path has no users yet and the old one has all of them.
26. **Verify the amending person's OWN code, not just "a" valid code.** `Views.verifyOwnCode` checks against the signed-in identity specifically: an admin's admin code, or that staff member's own account code. A staff code will not authorise an admin's amendment and vice versa. If this were relaxed to "any valid code", anyone on an unlocked device could amend records under someone else's name and the Amendments log would be worthless.
27. **User-supplied templates are untrusted input for escaping purposes, even though the user wrote them.** Every token value substituted into a custom template is HTML-escaped, because the *values* come from records (a party name, a note) that other people entered. Also: a template that throws must fall back to the built-in layout, never leave someone unable to print; and the in-app preview deliberately does not execute the template's JavaScript.
28. **Build one shared component for anything that appears in many forms.** The security-code field with its show/hide toggle is a single `codeField()` helper used everywhere. Re-implementing it per form is how alignment and behaviour drift apart — the toggle is absolutely positioned inside the field with matching input padding, and getting that subtly wrong in one place out of eight is the likely failure mode.
29. **If an importer creates missing records for one entity type, it must do so for ALL of them — or say loudly why not.** Parties and items were created on import; ships were match-only and silently dropped when unmatched. Nothing in the preview revealed the loss, so imported work quietly missed its ship link and per-ship profit was wrong. When adding a new linked field to any importer, either create-when-missing like the others or surface the skip in the preview. Silent partial linking is the worst of both.
30. **Match real-world names forgivingly, exact-match nothing that humans type freehand.** Ship names arrive as "MV Ocean Star", "M.V. OCEAN STAR", "mv ocean-star". `Match` (score, find, clusters, merge) strips case, punctuation, vessel prefixes and company suffixes and scores the rest, so a spelling slip is caught rather than saved as a second record. Exact matching here doesn't fail loudly — it silently creates a near-duplicate record beside the real one, which is far harder to notice and to undo.
31. **Hiding a deleted record from its own list is only a third of the job.** Every dropdown, picker and report that lists the same entity has to exclude it too, and each screen filtering for itself is how they drift apart — four places had. Always list through `activeParties()` / `activeShips()` / `activeItems()`. Note these intentionally do NOT affect `byId()` lookups, so a record already attached to an existing invoice keeps its name on historical documents.
32. **Prove data preservation against the real old file, not a mental model.** Step 80 boots the actual shipped v465 HTML, creates records, then reopens the same IndexedDB and localStorage with the current build and compares counts, invoice numbers and balances. Any schema or migration change should be re-run against this. One gotcha when testing it: the old window must `close()` its IndexedDB connection first, or it blocks the new build's version upgrade — the same real-world case the `IDB.open()` timeout exists for.
31. **"Can't read the data" must never render as "there is no data".** In local-only mode IndexedDB is the only copy. When `open()` fails (a blocked upgrade from another tab is the common case), every `getAll` returns `[]` and the app will happily render a normal empty dashboard — which looks exactly like catastrophic loss, and invites someone to re-enter work that then has nowhere to be written. `STATE._dbBlocked` guards this in three places now: `reloadAllData` shows the explanation, `boot()` must NOT call `renderView()` over it, and `UI.renderView()` keeps it up on every subsequent navigation. All three are required — the first two alone still let someone navigate to Sales and get an empty form.
32. **Test upgrades by actually upgrading, sharing BOTH IndexedDB and localStorage.** A new JSDOM window gets a fresh localStorage, so an upgrade test that only shares the IndexedDB factory silently lands on the setup/login screen and proves nothing. Pass a shared fake localStorage via JSDOM's `beforeParse` hook, and close the old window's DB connection first (`IDB.db.close()`) or the version bump is blocked and you are testing the blocked path instead of the upgrade path.
33. **When adding a soft-delete flag, audit every consumer, not just the list view.** A deleted party/ship/item must vanish from every picker so it can't be chosen again, while every existing record that references it keeps rendering and keeps counting in reports. Half-doing this in either direction is worse than not doing it: stale options reappear, or historic invoices lose their party and reported figures quietly change.
34. **When you fix a bug in one reversal path, grep for the pattern and fix every one.** The "mark voided AND post a reversing entry" double-removal was fixed in `voidInvoice`, but `voidPayment` and `voidAdvance` kept it for two more releases and were only caught by a later audit. `grep -n "reversed = origLines.map"` finds them all. The giveaway that this class of bug is present: the trial balance still reports balanced, because both sides move together — so assert on individual account balances (cash returns to its pre-payment value), never just that the books balance.
35. **Authorisation checks must verify the account is still ACTIVE, not merely that it exists.** `verifyOwnCode` matched the code against the staff account but ignored `archived`, so someone removed from the yard could still authorise edits and deletions with their old code. Any future check of this kind needs the active test alongside the identity test.
36. **A `<script>` tag inserted via `innerHTML` never executes.** The custom print template emitted the user's JavaScript as a script tag inside the rendered HTML, which meant the feature looked implemented and did nothing at all. Scripts must be run explicitly (`new Function(js)`), after the content is in the DOM, and wrapped so a failing script still leaves the document usable. Any future "let the user supply code" feature needs the same treatment — and a test that asserts an observable side effect of the script running, not merely that rendering didn't throw.
37. **Role gates need a headless-yard branch.** Anything gated on `role==='admin'` is unreachable on a yard with no admin. `isHeadlessYard()` exists for exactly this; the staff-accounts card was missed and left a solo operator unable to add a colleague. When adding any admin-only feature, decide explicitly what happens when there is no admin.
38. **The test suite lives in the repository.** An earlier 728-check suite existed only in a working directory and was lost when the environment was reset. It is now `tests/smoketest.js` (run it with `npm test`). Keep it in the repository and keep it growing.
39. **A `must-exist` assertion in a patch script proves the pattern exists, not that you patched the right copy.** `exportXLSXTable` and the all-tables workbook export contained near-identical lines; the patch hit the wrong one and every sanity check passed. Only a behavioural test (export, then read the rows back) exposed it. When a line looks generic, count occurrences first.
40. **Restyling a surface's background means grepping for inline colours that assumed the old one.** Making the sidebar light left the "Lock app" button in inline `#c7cdd1` — near-invisible, and the only desktop way to lock the app.
41. **Alias legacy tokens rather than rename them.** ~400 inline styles use `--rust/--slate/--good/--bad/--line`; they are now aliases of the design-language tokens, so the whole app re-themes without touching them. But an alias changes *meaning* where it changes *hue*: `--rust` is now near-black, so any chart that used it would have gone black. Charts have their own palette.
42. **Every amending action goes through `Views.reasonPrompt`.** Edit, delete, void, journal-delete, bank/staff edits. Voids were the gap for a long time precisely because they were built before the amendment log existed and nobody revisited them. When adding an action that changes or removes a record, route it there.
43. **Every column the app writes must exist in BOTH SQL constants** (`SQL_SCRIPT` and `SQL_MIGRATION_ADVANCES`). Local-only yards never notice a missing column; cloud yards get a stuck retry queue. A test now checks the known set — extend it when you add a written field.
44. **jsdom cannot see layout.** The harness proves rules and logic, not appearance. Anything visual (heights, wrapping, sheets, safe areas) needs a real device.

45. **Never delete a layout rule while restyling.** `.row > *, .field, .kpi, .card{ min-width:0; }` was overwritten by card styling; every input then shrank and text was cut off on phones. The test that "protected" the new look asserted the bug. Assert on behaviour (a real browser at 320/360/390px, `tools/uiaudit.py`), not on a selector's text.
46. **`toISOString().slice(0,10)` is the UTC date.** In UTC+6, before 6am it is yesterday. Use `todayISO()` / `isoDate(d)` (local date) everywhere; only Excel-serial arithmetic should use UTC.
47. **Do not assume `crypto.subtle`.** It is absent on plain `http://` pages (a copy on a LAN). Anything that hashes or signs must have a pure fallback, and the test harness has a `nosubtle` boot option to prove it.
48. **Enforce rules where data changes, not where forms are.** The closing date is checked in `DB.insert/update`, worker grants in `Ledger.*`, admin-only in the functions. A form guard alone is bypassed by an import, a package, a console or a second screen.
49. **Every import is: parse strictly, preview, confirm, apply all-or-nothing, prove, record, be undoable.** Any new import path must reuse `Importer` (or at least a single `Tx.run`, a duplicate check and a snapshot). Never write rows one at a time outside a transaction, never overwrite existing fields, never guess a value.
50. **Names are matched, not compared.** Anything a person types freehand (party, ship, item) goes through `Match.find`/`guardNew`; merged spellings are kept as `aliases` so they match silently next time. Merged-away records are marked `deleted` + `merged_into`, never removed.
51. **Opening balances are invoices with `opening:true`.** They must stay out of sales-by-customer/item/person reports and "today's sales" (`!i.opening`), but stay in balances, statements and ageing. Add the same filter to any new sales-type report.
52. **Add a column to both SQL scripts in the same change.** v730 added `aliases`, `merged_into`, `deleted`, `opening`, `import_batch`, `import_ref` and two tables; a test checks them. Cloud yards must re-run the SQL.
53. **Test the failure, not just the success.** The import and merge tests inject a throw part-way and assert the books are identical afterwards; the two-window test uses a fake `BroadcastChannel`. Keep doing that for any all-or-nothing claim.

54. **Never size anything with `vh` on a phone.** It is the tall viewport and ignores the keyboard; a sheet sized with it can sit partly off-screen with no way to scroll to its top. Use `--vvh` (visual viewport) and keep controls (Close/Back) in a fixed header that is not part of the scrolling content.
55. **A horizontally-scrolling wrapper must set `overflow-y` explicitly.** `overflow-x:auto` alone makes `overflow-y` compute to `auto`, and on real phones the wrapper then swallows vertical swipes.
56. **`select()` on a read-only field does nothing on iPhone; `navigator.clipboard` needs a secure context.** Use `copyText()`, and never say "Copied" unless it was.
57. **History: one entry per screen and per pop-up chain, and skip duplicates.** Closing a pop-up turns its entry into a duplicate the popstate handler skips. Never rely on `history.back()` alone: the in-app Back has a fallback for viewers that block it.
58. **Sign-in must not depend on identifying yourself first.** The code identifies the person; ambiguity is resolved by a chooser, never by asking everyone for an ID. WebAuthn needs https/localhost and a real hostname (not an IP), stores only the public key, and must be verified locally (challenge, origin, rpIdHash, UP flag, signature, counter).
59. **Mirror what sign-in depends on.** If the browser wipes IndexedDB, the accounts must come back from a second copy or the recovery tools become unreachable.
60. **A "covered by a reasoned amendment" exemption must be narrow.** `Amend.COVERED` lists transaction names that log their own entry; a broad rule (all `Ledger.*`) hid engine-level voids from the record.
61. **When a test passes because you called the engine directly, click the real button too.** The earlier suites passed while phone users could not close a pop-up. `tools/mobile_test.py`, `auth_e2e.py` and the sweeps drive real Chromium with touch.

62. **The invoice list and the ledger must not be allowed to disagree.** `receivablesTotal` clamps at zero, so an over-applied payment or advance still leaves the trial balance "balanced" while Accounts Receivable is over-credited. Guards live in the engine: `editInvoice` refuses a total below `paid` before it voids anything; `recordPayment` and `applyAdvance` refuse the wrong direction (sale = money in / customer advance; purchase and expense = money out / vendor advance), a different party, and more than is still owed. A missing bank on `recordAdvance` / `refundAdvance` must throw a clear error, not crash on `bank.account_id`.

63. **A checkbox inside `.field` must reset `min-height`, not only `height`.** `.field input` is 48px. `min-height` wins over `height`, so the tick stretches. Set `min-height` and `max-height` to 16px on checkbox and radio.

64. **Do not put `overflow-wrap: anywhere` on table cells.** It breaks party names, phones and money in the middle. Cells wrap on spaces; `.num` and `.right` stay `nowrap` and `.tbl-wrap` scrolls.

65. **Sample copy is neutral and Canadian English.** Default currency is ৳. Placeholders and sample data use the author's own made-up yard (HYC Yards Ltd, HYC Metals, HYC Rolling, and sample people such as Hamid Yasir and Iffat Mahjabin). Keep new examples made-up too. Do not put overflow-wrap:anywhere on numbers or table cells.

66. **byId is indexed.** It rebuilds when STATE._rev or the array length changes. DB writes bump STATE._rev. Do not cache balances across a write.

67. **In-file duplicates stay out until confirmed.** `filedup` rows are unticked. `go()` refuses ticked repeats unless `imp-dup-ack` is checked. Undo is `Importer.confirmUndo(batchId)`.

68. **Deleted is not the same as never existed.** Re-import matches voided and deleted invoices on date, party and total and leaves them unticked. A Yarding number that still exists, even if deleted, is skipped — restore it, do not mint a second number.

69. **Phone is the party identity.** `Match.digits` keeps the last 10 digits when longer, and ignores fewer than 8. `Match.byPhone` wins over name matching on import. Do not create a second party with the same phone.

## Design philosophy

Yarding is a yard book, not an accounting tutorial. Each screen asks what happened, how much, and who with. The ledger stays behind that. The voice is professional Canadian English: short, plain, no filler. Numbers never break mid-figure. The currency sign is the yard's own, defaulting to ৳. Sample names are the author's made-up ones (HYC Yards Ltd, Hamid Yasir). A party is identified by its phone number; the name is a label, and a number shared on purpose needs a tick and is noted on the record. Nothing is written until the person has seen the effect and confirmed it. A failed write rolls back. A void is a flag, not a second entry. Imports are all or nothing, duplicates stay unticked, and undo is always available. The interface is warm paper and ink, one primary action, no decoration that does not carry information.

70. **File names are the label.** `docFileName` builds INV_, receipt_, and Statement_ plus `fileStamp` (2026Oct02). Print sets `document.title` to that name and logs `print` with `whoAmI()`. Input audit runs only after a successful insert, never before, so a failed write is not eaten by the log.

71. **File names stay short.** `fileStamp` is `02Oct26`. `shortId` keeps the last 6 characters. Do not add the range twice.

72. **Do not clear a search on the first paint of a screen.** Clear `Views._listQ` only when the view actually changes. Backup names keep a 4-character suffix so two backups on one day do not overwrite.

73. **List search is `Views.searchList`.** It must live on Views. After redraw, focus the `[data-list-search]` input and restore the caret, or the first character is all that sticks.

74. **Account direction is checked before the invoice is written.** Sales take income, purchases take expense or asset, expenses take expense. Opening balances are the exception and post to equity. `voidInvoice` throws if the invoice is already voided.

75. **Credit notes reduce the unpaid balance and reverse income.** They do not refund cash. Do not seed convention accounts during an empty-database recovery. Current profit is already included in equity on the balance sheet.

76. **Backups carry a checksum.** Refuse the file if it does not match. JSON restore adds missing ids; replacing records that differ is opt-in, takes a snapshot first and is written to Amendments. Do not load a library from a CDN. Do not send the books to an outside service.

77. **A credit note is its own dated entry, taken off in proportion.** It is posted dated today and refused for an invoice dated inside a closed period (so a closed month never moves), splits the credit between income and Tax Payable in the invoice's own proportion, and reduces subtotal, tax, total and the tax breakdown together. It runs as one all-or-nothing unit, is permission-gated like editing the invoice, asks for a reason and the person's code, and is written to Amendments. An invoice that has a credit note cannot be edited; void it and enter a corrected one.

78. **Cloud is `CloudStore.connect(url, key)`.** It speaks PostgREST. Do not require the Supabase library. Supabase still works because it is PostgREST.

79. **Remote staff use the yard gate.** `STATE.config.gate` means the saved key is a yard pass, not the database key. The database key stays in the gate process (`YARD_KEY`).

80. **Cloud request headers are merged, not replaced.** A Prefer header must not drop the API key or the yard pass.

81. **The yard gate must catch upstream errors.** A failed store call returns 502. It must not send a body on GET or HEAD.

82. **User-facing errors say store, not Supabase.** Supabase remains one compatible store. The database key stays off employee devices.

83. **Invoice sheet values wrap.** `td.right` and `td.num` inside `#modal-root` must not stay nowrap, or a name or long ID is clipped. The balance uses `.due-hero` so the currency sign is not cut off. The harness must set `TextEncoder` on the window under jsdom 25.

84. **Phone sheet and bottom bar.** Detail tables inside the sheet use a fixed layout and must wrap. The bottom bar is inset 12px and keeps `padding-bottom:var(--safe-b)`. Close and back buttons are translucent, not solid.
